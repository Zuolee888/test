### static 静态代码块

```
static {
    System.loadLibrary("cyberpeace");
}
```

- `static {}`：**静态代码块**，类被加载的时候，**自动执行且只执行一次**

- `System.loadLibrary("cyberpeace")`：加载原生库

  - Android 系统会去加载 `libcyberpeace.so`

### Java方法链式嵌套分析

```java
if (str.equals(new String(Base64.decode(new StringBuffer(getFlag()).reverse().toString(), 0))))
```

Java 里**表达式是从内向外逐层求值**，每个方法都会返回一个结果，这个返回值直接当成外层方法的参数。

方法调用本身是一个**表达式**，有返回值；只要类型匹配，就可以直接塞进别的方法的参数位置，天然支持嵌套。

解法:逐层从内向外拆解执行顺序

```java
// 第1步：getFlag() 最先执行，返回原始字符串
getFlag()

// 第2步：拿到字符串，传给 StringBuffer 构造器
new StringBuffer(getFlag())

// 第3步：调用 reverse() 反转字符序列，返回StringBuffer自身
new StringBuffer(getFlag()).reverse()

// 第4步：toString()，把反转后的 StringBuffer 转成 String
new StringBuffer(getFlag()).reverse().toString()

// 第5步：把这个反转后的字符串传给 Base64.decode() 做解码
Base64.decode( 上面的字符串 , 0 )

// 第6步：Base64.decode 返回字节数组 byte[]，丢给 String构造函数，生成String
new String( 解码出来的byte[] )

// 第7步：最后用 str.equals( 这个最终字符串 ) 做相等判断
str.equals( 最终得到的字符串 )
```

## 底层语法规则

1. **方法调用是表达式，有返回值**
   不是只有变量才能当参数；只要一个调用能返回符合参数类型的值，就可以直接写在参数位置。
- `Base64.decode` 的第一个参数要求是 `String`
- `xxx.toString()` 返回正好是 `String` → 可以直接填进去
1. **链式调用和嵌套调用不是一回事（区分一下）**
- 链式：`a.b().c().d()` —— `b()` 返回对象，再调用这个对象的 `c()`
- 嵌套：`f(g(h()))` —— `h()` 返回值传给 `g`，`g` 返回值传给 `f`
  你这个代码里**两种同时存在**：
  `new StringBuffer(getFlag()).reverse().toString()` 是链式；外面包着 `Base64.decode(...)` 属于嵌套传参。
1. **可读性代价**
   逆向代码经常这么写：压缩代码、减少临时变量，增加阅读难度。
   正常开发不推荐写这么深的嵌套，不好调试（中间每一步的值没法单独打印观察）。

# Activity生命周期略解

##### 一,Activity 生命周期是一个状态机

Activity 不是你 `new` 出来自己调用方法的，而是由**系统（ActivityManagerService/ATM）通过回调驱动**。你重写这些回调，系统在状态切换时按固定顺序调用它们。你能做的是 "在正确的时机做正确的事"，而不能控制切换本身。

七个核心回调，按 "三对配对 + 一个重启" 记忆：

| 回调          | 进入的状态   | 核心职责                             | 是否可能之后直接被杀 |
| ------------- | ------------ | ------------------------------------ | -------------------- |
| `onCreate()`  | Created      | 一次性初始化：建界面、找控件、读数据 | 否                   |
| `onStart()`   | Started      | 界面变为可见                         | 否                   |
| `onResume()`  | Resumed      | 进入前台、获得焦点、可交互           | 否                   |
| `onPause()`   | Paused       | 失去焦点，暂停 / 保存，须快速返回    | 是（极端情况）       |
| `onStop()`    | Stopped      | 完全不可见，释放较重资源             | **是**               |
| `onDestroy()` | Destroyed    | 最终清理、注销                       | 不保证执行           |
| `onRestart()` | 回到 Started | 从 Stopped 重新显示前的过渡          | 否                   |

配对关系：

```
onCreate()  ↔ onDestroy()
onStart()   ↔ onStop()
onResume()  ↔ onPause()
```

## 三、逐个回调详解

### 1. onCreate (Bundle savedInstanceState) —— 静态分析第一入口

```
@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    setContentView(R.layout.activity_main);   // 你前面的例子是纯代码建 View
    //  findViewById、初始化变量、读取 getIntent()、建 ViewModel
}
```

- 整个生命周期**只执行一次**，负责所有一次性初始化。
- 参数 `savedInstanceState`：携带上次被系统回收 / 重建前保存的状态；首次启动为 `null`。
- **逆向意义**：这是反编译后定位程序逻辑的默认起点 —— 界面结构、按钮监听、关键初始化几乎都在这里。你前面的 `MainActivity` 就是把所有逻辑塞进了 `onCreate`。

### 2. onStart()

- Activity 变为**可见但还不能交互**（界面在后台渲染完成、尚未到前台）。
- 适合做与 "可见性" 绑定的初始化。实际开发中单独重写较少，常被 `onResume`/`onPause` 覆盖。

### 3. onResume()

- Activity 进入**前台、获得用户焦点、可接收输入**，用户真正 "正在用" 的状态。
- 适合：开启动画 / 视频 / 相机、注册传感器、刷新数据、恢复广播监听。
- 注意：弹窗、分屏失去焦点时会离开此状态。

### 4. onPause()

- 失去焦点、进入后台的第一步。被**半透明 Activity、对话框、分屏另一窗口**遮挡时只走 `onPause` 而**不走 `onStop`**（因为仍部分可见）。
- 职责：暂停动画 / 视频 / 相机等持续性操作、**把关键用户数据立即落盘**。
- **重要约束：必须轻量、快速执行**。因为新 Activity 的 `onResume` 要等当前 Activity 的 `onPause` 返回后才会执行，在这里做耗时操作会让跳转卡顿。
- 系统在内存紧张时可能在 `onPause` 后直接杀死进程，所以**只保证 `onPause` 一定执行，`onStop`/`onDestroy` 不保证**，关键持久化要放在这里。

### 5. onStop()

- Activity **完全不可见**。
- 可以做比 `onPause` 更重的释放：关闭数据库连接、注销较重的监听、释放不再需要的资源。
- 从这里进程随时可能被系统回收；用户返回时走 `onRestart → onStart → onResume`。

### 6. onDestroy()

- 销毁前最后回调，触发原因有两种，用 `isFinishing()` 区分：

  - 用户按返回键 / 调用 `finish()`：`isFinishing() == true`，真正结束；
  - 配置变更（如旋转屏）导致的重建：`isFinishing() == false`，系统马上会新建一个实例。

- 职责：注销在 `onCreate` 里注册的东西、清理线程 / 回调，防止内存泄漏。

- **不能依赖它做关键保存**：进程被系统杀死时它可能根本不执行。

### 7. onRestart()

- 仅在 Activity 从 Stopped 状态被用户重新唤回时触发，之后接 `onStart`。
- 适合恢复在 `onStop` 中释放、且重新显示时需要的资源。







在 JADX 里看包名就能判断类的来源：

- `com.example.helloandroid.*`：应用自己的类，一定能打开；
- `android.*`、`java.*`、`javax.*`：系统框架类，**打不开是正常的**；
- 第三方包名（如 `okhttp3.*`、`com.google.gson.*`）：被打包进了 dex，一般能打开；如果某个第三方类也打不开，说明它是 `compileOnly`（仅编译期引用、不打包）或在其他未加载的 dex 里。

```
  └── View
        ├── TextView
        │      ├── EditText
        │      └── Button
        ├── ImageView
        ├── ProgressBar
        └── ViewGroup（容器，本身也是 View）
               ├── LinearLayout
               ├── FrameLayout
               └── RelativeLayout
```

两个要点：

2. **`ViewGroup` 也是 View 的子类**，它是能装其他 View 的容器，所以 LinearLayout 本质上也是一个 View。
4. 所有 View 共有的能力都定义在这个基类里：`setPadding`、`setBackgroundColor`、`setOnClickListener`、`setOnApplyWindowInsetsListener` 等。你在 `MainActivity` 里对 LinearLayout 调这些方法，正是因为它继承自 View。

## 二、身份 2：作为 "变量 / 对象"—— 小写的 view

看你前面代码里的回调：

```
public final void onClick(View view) { ... }
//                    类型↑   ↑变量名
```

这里有两个词，别混：

- **`View`（大写 V）**：类型，说明这个参数是一个 View；
- **`view`（小写 v）**：变量名，只是给这个对象起的名字，代表 "被点击的那个控件"。

变量名是任意的，写成这样完全等价：

```
public final void onClick(View v) { ... }
public final void onClick(View abc) { ... }
```

JADX 反编译时习惯把参数命名为 `view`，因为 dex 里原本没有变量名。同理你还见过 `textView`、`editText`、`linearLayout`，它们都是**对象引用的名字**，不是类。

判断口诀：**大写开头、出现在类型位置 → 类；小写开头、出现在变量位置 → 对象。**

---

## 三、身份 3：作为 "包名"——android.view

```
android.view.View
└──包名──┘ └类名┘
```

View 这个类所在的包恰好叫 `android.view`。`LayoutInflater`、`WindowManager`、`MotionEvent`、`View` 都在这个包下。

这里的 `view` 是**包名的一部分**，和类名 View 只是英文单词相同，没有语法上的特殊关系。`import android.view.View;` 读起来像 "view 出现了两次"，其实一次是包、一次是类。

---

## 四、身份 4：View 后面带点号 —— 内部接口 / 内部类

你代码里出现过：

```
new View.OnClickListener() { ... }
new View.OnApplyWindowInsetsListener() { ... }
```

点号在这里表示 "**View 类内部嵌套的接口**"，不是包分隔符：

- `View.OnClickListener`：定义在 View 类里面的点击监听接口；
- `View.OnApplyWindowInsetsListener`：View 里的窗口边距监听接口；
- 类似还有 `View.OnFocusChangeListener`、`View.OnTouchListener`。

它们之所以嵌套在 View 里，是因为这些接口专门服务于 View 的事件机制。看到 `View.XXX`，要读成 "View 类的 XXX 成员"。

## 五、身份 5：作为多态引用 —— 声明是 View，实际可能是 Button

这是最容易让初学者困惑的点。回看你前面的两个合成方法：

```
lambda$onCreate$0(View view, WindowInsets windowInsets)   // 实际传进来的是 LinearLayout
lambda$onCreate$1(EditText editText, TextView textView, View view) // 实际传进来的是 Button
```

- 点击按钮时，`onClick(View view)` 里的 `view` **真实对象是 Button**，但参数类型声明为父类 `View`；
- 边距回调里的 `view` 真实对象是 `LinearLayout`，同样声明为 `View`。

这就是 Java 的**多态**：一个 View 类型的引用可以指向它的任意子类对象。因为监听接口是通用的，不可能为每种控件各写一套，所以统一用最通用的父类 `View` 接收。

逆向时要注意：**静态看到的 View 类型不等于运行时真实类型**。确认真实类型的方法：

```
view.getClass().getName();   // 运行时打印，例如 com.example...MainActivity$1 或 android.widget.Button
```

Frida 动态分析时同样可以用 `view.getClass().getName()` 看它到底是谁，再决定能不能强转成 Button、LinearLayout 等具体类型。

## 六、身份 6：方法名里的 View—— 只是 "视图" 这个英文单词

很多 API 名字里带 View，但这里的 View 是普通单词，不是在引用类：

表格

| 名称                   | 含义                                          |
| ---------------------- | --------------------------------------------- |
| `setContentView(View)` | 把一个视图设置为页面内容                      |
| `findViewById(int)`    | 按 ID 查找一个视图                            |
| `inflate(...)`         | 把 XML"膨胀" 成 View 对象                     |
| `ViewBinding`          | 视图绑定（Jetpack 组件）                      |
| `ViewCompat`           | View 的兼容工具类                             |
| 自定义 View            | 继承 View / 子类自己画控件，核心重写 `onDraw` |

这些词里的 View 取的是 "屏幕上一块视图" 的语义，不要把它当成新的类。

---

## 七、身份 7：架构里的 "View 层"—— 一个角色概念，不是类

在 MVC / MVP / MVVM 这些架构讨论中，还会出现 "View"，例如：

- MVP：Model - **View** - Presenter；
- MVVM：Model - **View** - ViewModel。

这里的 View 指**负责界面展示的那一层角色**（通常由 Activity、Fragment 担任），是一个**架构概念**，和 `android.view.View` 这个具体的类不是一回事。一个 Activity 是 "View 层"，但它本身继承的是 Activity，不是 `android.view.View`。看到架构文章要根据语境区分。
